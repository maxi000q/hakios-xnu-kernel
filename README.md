# HakiOS — iOS 6 app edition

English · [中文](README.zh.md) · [Українська](README.uk.md)

This fork turns an Android phone into an emulated iPhone 4 running iOS 6.1.3 —
as a normal installable app: no unlocked bootloader, no root, no flashing, no
fastboot. The emulator, the kernel loader and the display path are this
repository's own code; the iOS files themselves are never in the repository
and never redistributed — the app fetches the kernel cache straight from
Apple's own servers during install, the same contract the native path below
has always had.

The native 16.5 path of upstream — booting the stock iOS 16.5 user space on a
POCO X5 Pro through `fastboot boot` — is still here, still works, and is
described at the end of this file. The two halves share one tree; the app
edition added the emulator on the side rather than replacing anything.

## What the app is, exactly

Open it and the first screen says what it is doing, step by step, with a real
progress bar:

1. **creating the emulated iPhone's memory** — a 2.5 GiB sparse, storage-backed
   image (the guest is bounded by free disk space, not the process heap, and
   survives a process kill: "installed stays installed");
2. **fetching the kernel cache** — 7.4 MB out of the 938 MB iOS 6.1.3 IPSW on
   Apple's servers, by HTTP range requests (a phone does not pay for the
   other 930 MB);
3. **unpacking it** — inflated as it arrives;
4. **loading the kernel** — IMG3 container, optional AES-256 decryption with
   a key *you* supply (see below), `comp`/LZSS decompression, armv7 Mach-O,
   segments placed in the emulated iPhone's RAM at 0x80001000, exactly where
   an unmodified iOS 6 kernel is linked to run;
5. **first boot** — the engine's run thread retires instructions through the
   ARMv7 interpreter, 2M per frame, and presents the guest's 640x960 RGB565
   framebuffer through GLES 2 at a deliberate 30 fps.

Then the emulator screen: the guest's display, a status bar with the truth
(state, instructions retired, measured MIPS, how much of the guest is
resident), pause/resume, and halt reporting in the engine's own words —
reason, PC, the offending instruction word.

**Why 6.1.3 and not 6.1.6:** the roadmap guessed 6.1.6 and stage 4 verified
it against Apple's own archive: iOS 6.1.6 was never shipped for the iPhone 4
(it exists for the iPhone 3GS and iPod touch 4G only). The iPhone 4 line ends
at 6.1.3, build 10B329 — that is what this emulator installs
(`sysimage/ios6/README.md` has the member-by-member record).

## The two ways to boot

**The bundled self-test kernel** — no Apple code, no keys. A real armv7
program (752 bytes, generated by `scripts/gen_demo_kernel.py` with keystone,
wrapped in the real IMG3 → `comp`/LZSS → Mach-O chain) that fills and
verifies 64 KiB of guest RAM, paints every pixel of the framebuffer with a
checkable pattern, and powers off cleanly with `SVC #0x0FF`. It is the
kernel the desktop test rig runs, and the app offers it during install.

**Apple's kernel cache** — the real thing, AES-256 encrypted as Apple ships
it. The app asks for the key and IV of that exact file from your own
research; none are shipped, none are derived, nothing is circumvented (AES
is a public standard, and the loader refuses to guess: without a key it says
exactly that). With a key, the install places the actual iOS 6.1.3 kernel of
the iPhone 4 into the emulated machine.

**What boots after that, honestly:** this release's kernel path is real end
to end, but a research interpreter runs a 2012 kernel at "minutes to first
logo" pace, and the emulated iPhone has no drivers yet for the hardware a
full iOS 6 boot expects — touch, storage, the real display controller. The
first thing a real kernel does without them is halt, and the app will say
so in the kernel's own terms. Growing the machine (an HFSX volume behind the
stored system DMG, the devices XNU 2107 probes) is the work of the stages
after this one; the roadmap never promised a phone-in-an-app, and neither
does the app.

## Requirements

- Any Android 7.0+ device that installs the APK; the universal APK carries
  `arm64-v8a`, `armeabi-v7a` and `x86_64`.
- Actually *running* the guest needs a 64-bit process: the emulated
  iPhone's address space (RAM at 0x80000000, the A4's map, 2.5 GiB total) is
  one sparse mapping. Every Adreno 619 phone is 64-bit; on a 32-bit device
  the app says so instead of failing mysteriously.
- ~10 MB of data for the kernel cache and the written pages of the guest
  image; the ~860 MB system volume is deliberately **not** downloaded (this
  release has no consumer for it yet — the install screen says that too).

## Building and testing

```
make tests      # the desktop rig: stages 2-8, g++ -Wall -Wextra -Werror
make apk        # the app: Gradle + NDK, universal APK (arm64, v7a, x86_64)
```

The native core is one C++ tree compiled twice — by the NDK for the app and
by the host g++ for the tests — with no stubs in either build: the same
interpreter, memory, loader and renderer the phone runs are what CI executes
on a Linux runner. The rig's centrepiece is the whole-machine test: the
self-test kernel boots through every stage and its effects in guest memory
are checked byte by byte (`tests/test_demo_kernel.cpp`). That test found
three real bugs in the interpreter on its first run; a whole-machine test
earths its keep.

CI (`.github/workflows/` → see `ci/`) runs the rig, builds the APK on every
push, and enforces the repository's rules — including the one that matters
most: no file of iOS in the tree, ever.

## The ten stages

`ROADMAP.md` is the plan this fork executed; `docs/ios6-retarget.md` is what
changed when the plan met reality (the build is 6.1.3, the kernel is linked
at 0x80001000 so the guest's RAM moved to 0x80000000, the root filesystem
DMG is encrypted whole). One stage per commit, `stage N/10` in the log:
foundation, storage-backed memory, the ARMv7 interpreter, the image pipeline
and kernel loader, the Adreno 619 renderer, the engine and JNI bridge, the
app, the self-test kernel and rig, this README and CI, and the release.

## The native 16.5 path (upstream, unchanged)

HakiOS upstream runs the open-source XNU kernel (xnu-8796.121.2) with its own
boot loader and drivers on the POCO X5 Pro 5G (`redwood`, SM7325), booting
the stock iOS 16.5 user space natively — launchd, backboardd, SpringBoard —
through `fastboot boot`: nothing flashed, a session lives in RAM, a reboot
returns the phone to Android. The same system runs in QEMU (`virt`, aarch64).

The kernel is a patch to Apple's open-source XNU (`xnu/hakios.patch`, APSL
2.0) plus original drivers; the boot loader (`xnuloader/`), the user space
tools (`userland/`), the APFS tooling (`tools/apfs/`) and the device port
(`devices/poco-x5-pro/`) are the project's own. Everything that path needs —
the 16.5 IPSW members, the phone's own firmware — is fetched to your machine
from Apple's and the phone's own storage; nothing of it is committed.

```
make help        # the full map: fetch, images, kernel, loader, qemu, phone
```
